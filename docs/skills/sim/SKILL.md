# SIM: System Implement

Deliver a verified MVP from the current architecture/design document. Coordinate small subagent tasks, inspect actual behavior, and reconcile findings into the same document. Drive repairs autonomously within the active chunk; stop at verified chunk boundaries and ask the developer to proceed with a proposed next chunk. Stop the feature loop when the agreed MVP is fulfilled. Creating this skill or reviewing a design does not authorize implementing that feature.

## Establish scope and assess size

- Read the supplied SAP/SAD document, applicable project instructions, neighboring implementation, and available development skills. Resolve the actual document path rather than interpreting SAP as a particular product. Resume existing iteration state when present.
- Use the available `sad` skill for design updates and the project's normal development/review skills where relevant. Preserve developer-approved document structure, including additional subsections. User instructions take precedence over a skill template. If a supporting skill is unavailable, apply the conventions described here and record the limitation; do not pretend to have invoked it.
- Confirm that application implementation is authorized. A document marked design-only is not authorization by itself; a later explicit implementation instruction can authorize work. Scope, deployment, and permission choices already agreed with the user persist.
- Assess whether the requested work is a reasonable implementation chunk before editing application code. Use judgment: unrelated capabilities, multiple unresolved architectural choices, difficult ownership boundaries, or an inability to define one coherent acceptance scenario suggest excessive scope. Cross-layer work alone is not too large; a cohesive slice often needs domain, adapter, and test changes.
- When the feature appears too broad, stop before implementation and suggest a short ordered breakdown with acceptance outcomes, dependencies, and a recommended starting slice. Let the developer narrow the task. This is a guideline, not a file-count, line-count, or time threshold: do not stop routine work for arbitrary limits. If the developer has already chosen a workable breakdown, follow it and delegate within its slices.
- Establish the MVP boundary from explicit user decisions and the document. Resolve genuinely consequential gaps with the developer, while progressing on independent authorized work. Record routine implementation choices without reopening settled decisions.
- Map every relevant requirement ID to `MVP`, `deferred`, or `unresolved`, with an observable acceptance criterion. Explicitly deferred functionality is not an implementation defect. Do not silently defer a mandatory security, authorization, data-integrity, or compatibility requirement to get an MVP pass. A narrowed release scope that changes an existing obligation must be recorded as an agreed revision with stable IDs.

## Maintain compact iteration state

Use an existing task ledger if the project has one; otherwise adapt [assets/iteration-state.md](assets/iteration-state.md) next to the design document as `<feature>-implementation.md`. Track MVP acceptance, evidence, current work, blocking decisions, and deferred items. Keep the design as the source of requirements and architecture; the ledger holds execution state, not a second specification or accumulating transcript. Preserve enough state to resume without restarting completed work.

Maintain an ordered, developer-visible chunk checklist in that ledger. Give each chunk a stable ID, a concrete outcome, relevant requirement IDs, dependencies, and a status (`pending`, `active`, `blocked`, `verified`, or `deferred`). Check off only verified chunks and link their acceptance evidence. Keep unfinished and deferred work visible; completing a chunk does not complete the full feature. Refine future chunks as evidence improves without renumbering completed work or inventing detailed tasks for unresolved designs.

The parent owns this checklist and the next-step recommendation. Resume from it, update it after findings or scope changes, and identify the active chunk and proposed next chunk in progress reports. Do not leave the developer to reconstruct remaining work from previous chat messages.

## Run the feedback loop

1. **Select a slice.** Choose the smallest cohesive unfinished MVP outcome whose dependencies are ready. Identify requirement IDs, behavioral acceptance, code ownership, and validation before delegating. Reassess size when discoveries materially expand the slice.
2. **Delegate bounded work.** Use subagents for focused implementation, tests, inspection, or independent review. The parent owns the overall plan, integration, design document, and ledger. Give each worker the relevant design excerpt/IDs, repository instructions, allowed files, dependencies, non-goals, and required test/evidence report. Ask for changed files, actual commands/results, unresolved findings, and assumptions. Respect available concurrency; do not create agents merely to fill slots.
3. **Implement and test.** Follow the engineering practices below. Independently writable tasks may run concurrently; shared contracts, overlapping files, database fixtures, and dependent work must be sequenced. Agree shared interfaces first. Do not let workers overwrite each other, revert unrelated edits, independently change MVP scope, or run competing writes against a shared test instance.
4. **Integrate and inspect.** Review worker changes and assumptions, run relevant automated checks, then exercise the built feature through the actual runtime boundary. Use [references/runtime-validation.md](references/runtime-validation.md) for MCP/API, browser/UI, database, or background-processing inspection. For KITOS, also read [references/kitos.md](references/kitos.md). Prefer an independent inspecting/reviewing agent for substantial slices; provide requirements and actual artifacts, not the implementer's desired conclusions. Worker claims and green mocked tests alone are not runtime evidence.
5. **Classify and repair findings.** For a code defect, add an appropriate regression test and fix the implementation. For a missing requirement, ambiguous semantics, or unsupported design assumption, update the same SAP/SAD with the observation, evidence, proposed decision, and affected requirement IDs. Resolve routine choices within authorized scope; ask about changes to product behavior, access, trust boundaries, or MVP scope. Keep proposals distinct from agreed decisions. Address accepted MVP deficiencies in the next slice; defer enhancements explicitly. Never redefine acceptance merely to fit current code.
6. **Reconcile and repeat within the chunk.** Refresh affected scenarios, diagrams, Architecture, and Implementation; preserve requirement IDs and open decisions. Update the ledger/checklist with actual test/runtime evidence. After substantive fixes, rerun affected checks; repeat integration/runtime inspection when the changed boundary warrants it. Avoid repeating unchanged broad suites without a reason. Continue repairing the active chunk until its acceptance is verified; then follow the chunk handoff below.

Document updates are part of each iteration, not an approval step at the end. Do not change the design for an ordinary code bug unless it exposed a requirement or design deficiency.

## Engineering practices

- **DDD:** use the project's domain vocabulary, bounded contexts, aggregates, and value objects where they express real rules. Keep business invariants in the appropriate domain/application layer and infrastructure/protocol concerns in adapters. Follow existing conventions instead of introducing a parallel framework or speculative entities.
- **SOLID:** keep responsibilities cohesive, dependencies explicit and injected, and interfaces focused on actual consumers. Preserve dependency direction and substitution contracts; introduce abstractions where they isolate real variability or improve testing, not an interface for every class.
- **TDD where useful:** for domain rules, validation, permissions, regressions, and deterministic query behavior, write a behavioral test, verify a meaningful failure, implement the smallest passing change, and refactor. Test-first need not be forced onto exploratory wiring or low-impact formatting; runtime/application logic still requires meaningful automated coverage.
- **Automated testing:** cover intended outcomes and relevant failures, boundaries, concurrency, and authorization. Use deterministic fixtures and the existing test stack. Avoid tests that copy implementation, only assert mocks, or weaken assertions to hide defects.
- **Integration testing:** each larger slice crossing protocol, authentication, dependency injection, serialization, persistence, or service boundaries needs representative integration tests against actual collaborating components. Identify which dependencies are real or stubbed; mocked components do not prove the properties they replace. Use disposable fixtures and exercise ordinary and denied identities, not only administrators.
- **Operational quality:** apply the project's formatting, analyzers, code-quality/review skill, error/result conventions, logging, cancellation/timeouts, transaction/event rules, compatibility, and query limits where relevant. Fix failures at their source; do not relax required gates to obtain green. Avoid unrelated refactoring and unneeded dependencies.

## Stop and hand off at verified chunk acceptance

At a verified chunk boundary, stop implementation and mark the chunk complete in the checklist. Summarize its observable result and evidence, distinguish chunk completion from full-feature MVP completion, and proactively select the smallest useful next chunk. Explain its intended outcome, requirement IDs, dependencies or unresolved decisions, and how it will be verified. Recommend a concrete next action rather than asking the developer to invent the plan. If a consequential decision blocks implementation, propose resolving that decision as the next step with a recommended option and tradeoffs.

Ask explicitly whether to proceed with the proposed next chunk, and wait for the developer's reply before starting it. This handoff is the developer's requested checkpoint even when the overall feature has already been authorized. A reply such as "proceed" selects the proposed chunk; retain prior authorization and settled decisions. Do not ask again for repairs, delegation, or ordinary validation within that chunk. Do not start another chunk in the same turn or interpret silence as agreement.

## Stop at verified MVP acceptance

Stop implementing immediately when all MVP acceptance criteria have evidence, required automated/unit/integration checks and project quality gates pass on the final integrated state, representative runtime inspection passes, and no unresolved decision or blocking deficiency prevents an MVP requirement from being met. The design and ledger must reflect the implemented behavior and limitations. Do not continue into deferred features, speculative optimization, or production rollout.

If required validation cannot run, record the exact missing dependency/environment and mark the corresponding acceptance `unverified`; do not call the MVP complete. Continue independent useful work. If a genuine external blocker remains, report it and the concrete next action. Do not retry an unchanged environmental failure indefinitely; change the approach when evidence supports it, and never treat an iteration budget or exhausted time as proof of success.

Finish with the chunk/MVP outcome, checklist and design paths, passed checks and runtime evidence, material limitations, and remaining scope. When MVP work remains, end with the proposed next chunk and the proceed question. When the full agreed MVP is verified, report completion and stop without proposing deferred enhancements as required next work. Do not deploy, merge, publish, or contact others without authorization for those actions.
